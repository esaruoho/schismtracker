# Escalation Requests

Commands are run outside the sandbox if they are approved by the user, or match an existing rule that allows it to run unrestricted. The command string is split into independent command segments at shell control operators, including but not limited to:

- Pipes: |
- Logical operators: &&, ||
- Command separators: ;
- Subshell boundaries: (...), $(...)

Each resulting segment is evaluated independently for sandbox restrictions and approval requirements.

Example:

git pull | tee output.txt

This is treated as two command segments:

["git", "pull"]

["tee", "output.txt"]

Commands that use more advanced shell features like redirection (>, >>, <), substitutions ($(...), ...), environment variables (FOO=bar), or wildcard patterns (*, ?) will not be evaluated against rules, to limit the scope of what an approved rule allows.

## How to request escalation

IMPORTANT: To request approval to execute a command that will require escalated privileges:

- Provide the `sandbox_permissions` parameter with the value `"require_escalated"`
- Include a short question asking the user if they want to allow the action in `justification` parameter. e.g. "Do you want to download and install dependencies for this project?"
- Optionally suggest a `prefix_rule` - this will be shown to the user with an option to persist the rule approval for future sessions.

If you run a command that is important to solving the user's query, but it fails because of sandboxing or with a likely sandbox-related network error (for example DNS/host resolution, registry/index access, or dependency download failure), rerun the command with "require_escalated". ALWAYS proceed to use the `justification` parameter - do not message the user before requesting approval for the command.

## When to request escalation

While commands are running inside the sandbox, here are some scenarios that will require escalation outside the sandbox:

- You need to run a command that writes to a directory that requires it (e.g. running tests that write to /var)
- You need to run a GUI app (e.g., open/xdg-open/osascript) to open browsers or files.
- If you run a command that is important to solving the user's query, but it fails because of sandboxing or with a likely sandbox-related network error (for example DNS/host resolution, registry/index access, or dependency download failure), rerun the command with `require_escalated`. ALWAYS proceed to use the `sandbox_permissions` and `justification` parameters. do not message the user before requesting approval for the command.
- You are about to take a potentially destructive action such as an `rm` or `git reset` that the user did not explicitly ask for.
- Be judicious with escalating, but if completing the user's request requires it, you should do so - don't try and circumvent approvals by using other tools.

## prefix_rule guidance

When choosing a `prefix_rule`, request one that will allow you to fulfill similar requests from the user in the future without re-requesting escalation. It should be categorical and reasonably scoped to similar capabilities. You should rarely pass the entire command into `prefix_rule`.

- `<short-prefix>.*<literal>` where `<short-prefix>` is 1-2 characters — e.g. `M.*King`, `A.*Smith`, `X.*Energy`
- `<TOKEN>.*<TOKEN>.*<TOKEN>` — three or more `.*` segments separated by literals
- Alternations where any side contains greedy `.*` followed by a long literal — e.g. `"foo\|bar.*baz.*qux"`, `"X.*Y\|A.*B.*C.*D"`
- Any regex whose backtracking complexity is non-obvious. **If you can't say "this is O(n) for input of length n", do not run it.**

### Required practice — USE THESE INSTEAD

**Default to ripgrep fixed-string mode (`rg -F`).** Multi-pattern: `rg -F -e "literal1" -e "literal2" -e "literal3"`. Almost always faster than grep, always safe from backtracking.

**For filename triage**, use `find -iname` first: `find . -iname "*Marianna*King*"`. Bounded by file count, never explodes.

**For literal-string content search**, use `rg -F "exact phrase"` or `grep -F "exact phrase"`. Fixed-string mode disables regex engine entirely.

**If you genuinely need regex, anchor literals tightly**: `"Marianna_king@adams\.edu"` is safe; `"M.*King"` is not.

## 🔴 MANDATORY: `cp` AND `mv` ARE ALIASED TO `-iv` ON ESA'S MACHINE — A SCRIPTED OVERWRITE WILL HANG, NOT FAIL

**Esa's `~/.bash_profile` (lines 1271–1272) sets:**

```bash
alias cp="cp -iv"
alias mv="mv -iv"
```

**The Codex Bash tool initializes its shell from that profile, so these aliases ARE live in every Bash call I make.** `rm` is *not* aliased — only `cp` and `mv`.

### What actually goes wrong — TWO failure shapes, and the quiet one is worse

`-i` means *prompt before overwriting an existing file*. In a tool call there is nobody to answer, and what happens next depends on what stdin is attached to:

- **It blocks.** If stdin stays open (e.g. the call also used a heredoc), `cp` waits forever on `overwrite <file>? (y/n [n])`. The harness times out and backgrounds the call, which reads like a mysterious hang, and an orphan process sits on stdin until killed.
- **It silently declines.** If stdin is at EOF, `cp` takes the default answer — *no* — and returns non-zero. **Verified 2026-08-08: it can do this printing NOTHING at all.** No prompt text, no error, no output. The destination simply still holds its old content.

Both shapes leave the **destination untouched** and any `&&` chain unexecuted. The silent one is the dangerous one, because at a glance the call looks like it worked.

**Diagnostic:** if a Bash call inexplicably backgrounds/times out, read the output file and look for `overwrite <path>? (y/n [n])`. And after *any* scripted copy, if correctness matters, verify the destination actually changed (`wc -l`, `md5`, a `grep` for something only the new version has) rather than trusting exit status.

### The rule

1. **Prefer the `Write` / `Edit` tools over shell copies for file content.** They never prompt, and they keep the harness's file-state tracking correct. Reach for the shell only when it is genuinely a filesystem operation.
2. **When you must copy in a script or tool call, bypass the alias explicitly.** All four verified working on 2026-08-08 (destination actually changed):
   - `command cp SRC DST` — cleanest, bypasses alias lookup entirely ✅
   - `/bin/cp SRC DST` — absolute path, same effect ✅
   - `\cp SRC DST` — backslash suppresses alias expansion ✅
   - `cat SRC > DST` — when the goal is really "make DST have SRC's content" ✅
3. **`cp -f` DOES NOT WORK — do not use it as the bypass.** Verified twice on 2026-08-08: `cp -f src dst` expands to `cp -iv -f src dst` and *still* declines the overwrite, leaving the destination stale. The BSD man-page claim that "the last of `-f`/`-i`/`-n` takes precedence" does not hold here. Same for the un-bypassed plain `cp` and plain `mv` — both left `dst=OLD`.
4. **Same bypasses for `mv`** — `command mv`, `/bin/mv`, or `\mv`. Verified: plain `mv` leaves the destination stale; `command mv` works.
5. **Never chain an un-bypassed `cp`/`mv` with `&&`.** If it prompts or declines, everything downstream silently does not happen.
6. **Gotcha — a wrapper hides the alias.** Aliases are only expanded when the word is in *command* position, so `timeout 4 cp src dst`, `xargs cp`, `find -exec cp`, and `sudo cp` all get the raw `/bin/cp` with no `-i`. That is why some scripted copies work and others do not. Do not use this as the bypass (it is accidental); just know it when explaining behaviour.
7. **Do not "fix" this by editing `~/.bash_profile`.** The aliases are a deliberate safety net Esa set for his own interactive use (from natelandau's bash_profile). My tooling adapts to his environment, not the reverse.

The heredoc wrote fine; the `cp` hit the overwrite prompt and blocked. The call timed out into the background, `wc -l` never ran, and `Source/SymphonicHarmonics.h` still held the **old 757-line** version while I believed the 811-line rewrite had landed. I only caught it because the line count looked wrong. A delayed `killed` task-notification for that same command arrived much later in the session, long after I had worked around it — noise that cost a second round of investigation.

Cost: one wasted tool call, one stale-file near-miss on a file I was actively rewriting, and a confusing orphan notification.

### Single-sentence statement
